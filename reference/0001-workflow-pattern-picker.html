Choose control flow before choosing agents.

Start with the dependency between steps. Then select the least autonomous pattern that expresses it.

  1. Single agent - One model-backed role can complete the task, optionally using tools. Keep this as the baseline.
  2. Sequential orchestration - The next stage runs after the previous stage and consumes its output. Example: draft, then review.
  3. Concurrent orchestration - Independent specialists work from the same input; collect or aggregate their separate results.
  4. Handoff orchestration - The next owner depends on the conversation; one agent transfers control to a specialist.
  5. Group chat orchestration - A manager chooses speakers for bounded, iterative collaboration over shared conversation history.
  6. Magentic orchestration - A manager plans and replans a complex task, choosing participants dynamically. Keep rounds, stalls, and resets bounded.
  7. Explicit graph with conditional edges - Use typed workflow executors and conditions when the application owns routing, deterministic gates, or bounded loops.

A fast decision path

Can one agent do it? Stay single-agent. If not: fixed dependency means sequential; independent work means concurrent; conversational ownership changes mean handoff; repeated shared discussion means group chat; open-ended decomposition means Magentic. If the application must enforce a condition or loop, model that control flow explicitly in a graph.

For the course project: Planner -> Worker -> deterministic Validator, with a failure-only return to Worker and a small retry limit, points to an explicit workflow graph. A test/build validator is ordinary code; it does not need to be another agent.

Do not call a workflow "better" because it has more agents. Run the same representative tasks through the current single-agent baseline and the workflow, then compare task checks and output quality. The Agent Framework evaluation docs support local evaluators, repeated runs, and per-agent workflow breakdowns.
