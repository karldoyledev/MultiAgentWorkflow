Microsoft Agent Framework / Lesson 1

Choose the control flow before the agents.

A workflow earns its complexity by making dependencies, routing, or validation explicit.

About 4 minutes / One design decision / C# project

You already have a working agent call. Keep it: that is the baseline your workflow must beat. Adding roles alone does not improve an answer; orchestration is useful when the task has a meaningful structure that one call does not express clearly.

The decision question

Ask: what must happen next, and who or what decides? That question selects a workflow shape more reliably than starting with "How many agents should I create?"

  • Single agent: one role can complete the task, optionally using tools. Tools can extend its capability without adding another agent.
  • Sequential orchestration: known stages run in a fixed order, with each stage consuming work from the previous one.
  • Concurrent orchestration: independent agents work from the same input; compare or aggregate their results.
  • Handoff orchestration: ownership changes with the conversation as one agent transfers control to a specialist.
  • Group chat orchestration: agents take bounded, iterative turns over shared conversation history.
  • Magentic orchestration: a manager plans, delegates, tracks progress, and replans when the path cannot be fixed up front.
  • Explicit graph with conditional edges: the application enforces branches or retry rules using workflow executors and conditions.

The .NET workflow API models executors connected by edges. A built-in sequential orchestration is appropriate for a straight line; a custom graph is the better fit when your own code needs to decide whether a result passes or loops back.

Apply it to your first system

Start with three stages, but only two need a model:

Request
  |
Planner (agent) -> Worker (agent) -> Validator (tests/build)
                         ^                 |
                         +---- fail -------+  (bounded retries)
                                           |
                                         pass -> Result

The planner and worker are model-backed agents. The validator should first be deterministic code: run tests, inspect a structured result, or check an invariant. A failed check routes the diagnostics back to the worker; success exits. A retry cap prevents an unbounded loop. This is an explicit graph, not just a sequence, because the validator controls a branch.

Keep the win measurable. Before adding agents, choose a small set of representative tasks and a clear pass condition. Compare the existing single-agent response with the workflow on those same tasks. Track correctness/reliability; also note extra model calls and elapsed time so quality gains are not considered in isolation. The framework supports local evaluators, repeated runs, and per-agent evaluation results.
